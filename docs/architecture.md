# Архитектура Wolfy

Документ отвечает на три вопроса: из чего собрано приложение, где проходят границы
между частями и по каким контрактам эти части разговаривают. Правила правки каждого
слоя — в `rules/`; здесь только связи.

---

## 1. Четыре части и линия раздела

```text
client/ Compose (Android, Windows, Linux) ── C-FFI ─┐
                                                    ├── core/ Rust
web/ React PWA ─────────────────────────── WASM ────┘
       │                                             локальное чтение,
       └────────────── HTTP + JSON ─┐                грамматика, SRS
client/ ────────────── HTTP + JSON ─┴── server/ Go ── Postgres
                                        сеть, файлы, схема `wolfy`
```

Наружу из сервера ведут: Читавук (аккаунты), DeepL (перевод), OCR и AI-провайдеры,
Google и Яндекс (социальный вход), Gutendex/Project Gutenberg (каталог) и RSS-источники
газеты. Клиент не ходит ни к одному из них напрямую — иначе ключи провайдеров
пришлось бы положить в приложение, которое можно распаковать.

Граница между ядром и сервером проходит по одной линии — **нужна ли сеть**.

Тап по слову обязан отвечать мгновенно, поэтому всё, что можно посчитать на
устройстве, считается в Rust: разбор словоформы, лемма, часть речи, частотность,
грамматические конструкции предложения, синтаксические роли и поиск в скачанном
словаре. Это работает в метро и в самолёте.

Сеть нужна там, где локально не получится: контекстный перевод (DeepL знает
предложение целиком лучше любого словаря), синхронизация между устройствами,
распознавание страницы по фото, лента открытых изданий и раздача обновлений. Это
делает Go-сервер — заодно потому, что ключи провайдеров нельзя класть в приложение,
которое можно распаковать.

Граница между клиентом и ядром проходит по другой линии — **есть ли здесь экран**.
В ядре нет ни одного решения о том, как выглядит интерфейс, но есть все решения о
том, что показывать: какой глагол в предложении сказуемое, когда карточка снова
станет к повторению, какая книга открыта последней.

## 2. Карта кода

### `core/` — Rust

| Модуль | Что делает |
|---|---|
| `parser/` | Открывает книгу: `epub.rs`, `txt.rs`, `pdf.rs`. Глава отдаётся по требованию, поэтому открытие не зависит от объёма книги. `mod.rs::open` выбирает парсер по расширению и возвращает внятную ошибку на неизвестный формат |
| `tokenizer/` | Режет текст на токены и предложения. Токен несёт свои границы в исходной строке — по ним клиент подсвечивает слово, не пересчитывая текст |
| `lexicon/` | Встроенный словарь форм: `english_lexicon.tsv` (1,8 МБ) через `include_str!`, разбирается лениво по `OnceLock` — при старте не тратится ничего. `morphology.rs` объясняет словоформу, `verbs.rs` — неправильные глаголы, `pos.rs` — части речи |
| `tagger/` | Разметка предложения частями речи; `function.rs` отделяет служебные слова от знаменательных |
| `grammar/` | Движок разбора: 17 детекторов правил, по файлу на правило. `chain.rs` — общий фундамент (группа сказуемого и её звенья), `roles.rs` — синтаксические роли и грамматические маркеры, `reference.rs` — 57 справочных статей, `exercise.rs` — генератор упражнений |
| `srs/` | Интервальные повторения: `scheduler.rs` (интервалы, HP, забывание, время напоминания), `card.rs`, `drill.rs` (пять видов тренировки), `chunks.rs` (разбиение фразы на блоки для конструктора), `intensity.rs`, `training.rs` (очередь и статус колоды) |
| `library/` | Книги, полки, прогресс, словари книг: `ops.rs` — операции, `merge.rs` — слияние локального состояния с серверным |
| `dictionary/` | Чтение офлайн-словаря: русский эквивалент, английское толкование, МФА |
| `settings.rs`, `practice.rs` | Настройки приложения и отдельный CRDT прогресса тренировок. Новые поля читаются со значениями по умолчанию из старых файлов |
| `clock.rs` | Локальный день и час из UTC-миллисекунд и смещения **в минутах**. Своих часов у ядра нет |
| `ffi/` | Единственная дверь наружу: `mod.rs` — точки входа, `dto.rs` — формы ответов, `session.rs` — команды сессии |

Ядро не знает, который час, в какой временной зоне читатель и какие бывают UUID.
Всё это приходит параметрами. Причина не в эстетике: часы и генератор случайностей
внутри библиотеки делают её нетестируемой, а логику сдвига дат — недоказуемой.

`#![deny(clippy::unwrap_used, clippy::expect_used)]` вне тестов: битая книга обязана
вернуться ошибкой, а не уронить читалку.

| Пакет | Что делает |

| `cmd/updater` | Отдельный маленький процесс: ставит MSI после закрытия Wolfy. Едет внутри установщика |

### `client/` — Kotlin Compose Multiplatform

Наборы исходников: `commonMain` (почти всё), `jvmSharedMain` (общее для Android и
desktop — JNA-мост, файловое хранилище, загрузчик обновлений, loopback для OAuth),
`androidMain`, `desktopMain`.

| Каталог | Что делает |
|---|---|
| `ffi/` | `WolfyCore.kt` — интерфейс к ядру, `JnaWolfyCore.kt` — реализация через JNA |
| `data/` | `WolfyApi.kt` — весь HTTP, `SyncService.kt` + `SyncDto.kt` — синхронизация, `AccountSession.kt` — токен и его хранение, `Settings.kt`, `library/` — библиотека поверх сессии ядра, `dictionary/` — установка офлайн-словаря |
| `platform/` | `expect`-объявления и реализации Android/desktop: выбор книги и фото, произношение, напоминания, drag-and-drop, браузер OAuth, обновления, звуки, имя устройства |
| `theme/` | `Colors.kt` — четыре темы и палитра грамматических семейств, `Typography.kt`, `Motion.kt` — длительности и кривые движения |
| `ui/` | Экраны: `reader/`, `card/`, `library/`, `decks/`, `srs/`, `discovery/`, `reference/`, `settings/`, `account/`, `onboarding/`, `nav/` (нижняя панель, горячие клавиши, шпаргалка). `WolfyApplication.kt` — корень: разделы, маршруты, глобальные клавиши |
| `widgets/` | Общие детали: `ReaderText.kt`, `DropCap.kt`, `SentenceGraph.kt` и `SentenceTree.kt` (граф связей), `PhraseBlocks.kt`, `DragBoard.kt` (пятнашки), `Flight.kt` (полёт слова в колоду), `Flame.kt` (серия), `WolfyCompanion.kt` и `WolfySticker.kt` (маскот), `Appear.kt`, `Buttons.kt`, `Pressable.kt` |
| `srs/` | `TrainingViewModel.kt`, `Drill.kt` — тренировка поверх команд ядра |

Компаньон живёт в `data/companion` и `ui/companion`; в читалке он скрыт за
краевым ярлычком и появляется только по жесту/клику. Слои внешности берутся из
валидированного runtime-пака, а не из произвольных SVG. Звуки и уменьшение движения
— независимые синхронизируемые настройки.

`CompanionMemoryRepository` хранит на устройстве точный кэш ИИ-ответов,
ограниченную историю запросов и контрольные точки кратких пересказов по книгам.
Исходный текст страниц не сохраняется: в ключе остаётся только отпечаток. Память
не входит в sync, имеет три предела объёма и очищается отдельно от библиотеки.
При новом запросе сервер получает не более 3500 знаков выжимки как недоверенные
данные; попадание в локальный кэш вообще не обращается к серверу и не тратит квоту.

### `web/` — React + TypeScript PWA

`web/src/core` — мост к тому же Rust-ядру через WASM, `reader` — читалка,
`companion` — редактор, рендер слоёв и локальный движок реакций, `sync` — тот же
серверный обмен, `storage` — OPFS/IndexedDB. Браузерный интерфейс повторяет
контракты native-клиента, но не копирует его view-model: владельцем библиотечного
состояния всё равно остаётся Rust-сессия.

Браузерная память компаньона повторяет те же лимиты и ключи поведения, но лежит
в `localStorage`: книги продолжают храниться отдельно в OPFS.

## 3. Связи: три контракта

### 3.1. Клиент ↔ ядро: C-FFI, JSON внутри строк

Один способ разговора на native-платформах: Android и Linux грузят `.so`, Windows —
`.dll`; вызовы одинаковые. Web вызывает те же операции через WASM-мост.

**Правила границы.**

- Каждая точка входа обёрнута в `catch_unwind`. Паника в Rust, перешедшая границу
  FFI, — это неопределённое поведение, а не исключение.
- Ошибка возвращается как `null`, текст берётся отдельным вызовом
  `wolfy_last_error()`.
- Любая строка, полученная из ядра, освобождается **только** `wolfy_string_free`.
- Клиент разбирает ответы с `ignoreUnknownKeys = true`: новое поле в ядре не ломает
  старый клиент.

**Точки входа.**

| Группа | Функции |
|---|---|
| Разбор | `wolfy_analyze_word`, `wolfy_tokenize`, `wolfy_explain` |
| Книга | `wolfy_book_open`, `wolfy_book_metadata`, `wolfy_book_chapter`, `wolfy_book_close` |
| Справочник | `wolfy_grammar_reference`, `wolfy_grammar_exercises` |
| Сессия | `wolfy_session_open`, `wolfy_session_run`, `wolfy_session_library`, `wolfy_session_settings`, `wolfy_session_dirty`, `wolfy_session_saved`, `wolfy_session_close` |
| Служебное | `wolfy_version`, `wolfy_last_error`, `wolfy_string_free` |

**Сессия** — центральная часть. Это владелец всего изменяемого состояния: библиотеки,
колод, настроек. Клиент не правит эти данные сам, а посылает команду:

```
wolfy_session_run(handle, {"op": "save_word", "bookId": …, "lemma": …, "now": …})
   → {"library": true, "settings": false, "card": {…}}
```

Ответ говорит, что изменилось, и клиент решает, что перерисовать и что сохранить на
диск. `wolfy_session_dirty` отдаёт то, что ещё не записано; `wolfy_session_saved`
подтверждает запись. Команд около сорока — от `add_book` и `save_phrase` до `review`,
`due`, `training_queue`, `set_theme` и `apply_server`.

Время и свежие идентификаторы **всегда приходят в команде**, потому что часов у ядра
нет. Смещение зоны — в минутах, а не в часах: Индия живёт на +5:30, Непал на +5:45,
и деление на часы сдвигает им границу дня.

### 3.2. Клиент ↔ сервер: HTTP + JSON

| Метод и путь | Доступ | Зачем |
|---|---|---|
| `GET /healthz` | открыт | Живость и список включённых возможностей |
| `POST /v1/auth/login` | ограничитель | Вход через Читавук |
| `POST /v1/auth/register` | ограничитель | Регистрация. Ответ **202** и `{verificationRequired, email}`, а не сессия |
| `POST /v1/auth/resend-verification` | ограничитель | Повторное письмо |
| `POST /v1/auth/google/start`, `GET …/callback` | ограничитель / открыт | Google: PKCE на сервере |
| `POST /v1/auth/yandex/start`, `…/complete` | ограничитель | Яндекс: одноразовый код |
| `POST /v1/translate` | ограничитель, **без аккаунта** | Контекстный перевод |
| `GET /v1/define`, `GET /v1/dictionary` | открыт | Толкование и архив словаря |
| `GET /v1/update/latest`, `GET /v1/update/files/{name}` | открыт | Обновления: проверка начинается до входа |
| `GET /v1/me` | по токену | Кто вошёл |
| `POST /v1/sync` | по токену | Синхронизация |
| `PUT/GET /v1/books/{bookId}/file` | по токену | Загрузка и получение файла книги на другом устройстве |
| `POST /v1/ocr` | по токену | Страница по фото |
| `POST /v1/ai/phrase`, `/v1/ai/recap` | по токену, квота | Объяснение фразы и пересказ прочитанного |
| `POST /v1/ai/companion/{opinion,question,pack}` | по токену, квота | Явные ИИ-действия компаньона |
| `GET/PUT /v1/discovery/profile`, `GET /v1/discovery/feed`, `POST /v1/discovery/items/{id}/like`, `…/add` | по токену | Лента открытых изданий |

Что открыто без аккаунта — решение продуктовое, а не техническое. Перевод и словарь
работают в первую же минуту после установки: требовать регистрацию за то, ради чего
приложение и ставят, — верный способ его удалить. Ограничитель частоты стоит там,
где за запросом стоит платный сервис или чужая система: он пропускает залп (трудная
страница разбирается подряд) и останавливает того, кто гонит книгу целиком.

Ошибка везде одной формы: `{code, message}`, где `message` — человеческий текст
по-русски, годный к показу без перевода в клиенте.

### 3.3. Синхронизация

Last-write-wins по ревизии, которую присваивает сервер. Каждая синхронизируемая
запись несёт `rev`, время правки и признак удаления — удаление это пометка, иначе оно
не доедет до второго устройства.

Исключение одно: **прогресс чтения**, где побеждает не последняя запись, а наибольшая
позиция. Иначе телефон, читавший офлайн, откатит прочитанное на ноутбуке.

Слияние библиотеки живёт в ядре (`library/merge.rs`), а не в клиенте: правило одно на обе
платформы, и разъезжаться ему нельзя. Клиент шлёт `apply_server` с ответом сервера и
получает обратно и новое состояние, и то, что нужно отправить дальше.

Общая модель данных описана в `rules/shared_protocol.md`. Сейчас DTO держатся
согласованными вручную в трёх местах — `core/src/ffi/dto.rs`,
`server/internal/store/sync.go`, `client/…/data/SyncDto.kt`; отдельного `proto/` с
кодогенерацией пока нет, и это осознанный долг, а не забытая папка. Профиль
компаньона едет в том же sync-ответе, практика — отдельным CRDT-контрактом, а байты
книги — отдельными `PUT/GET`: смешивать крупный файл с LWW-метаданными нельзя.

### 3.4. Сервер ↔ Читавук: общие аккаунты

Читавук выпускает непрозрачный сессионный токен. Wolfy хеширует его SHA-256 и
проверяет по общей таблице `sessions`, откуда получает `user_id`. Своей регистрации у
Wolfy нет — иначе появятся два пользователя с одной почтой.

Форма входа и форма регистрации передают почту, пароль и описание устройства
(`{id, name, platform}`) в API Читавука. Wolfy сохраняет только полученный токен на
конкретном устройстве; пароль через свою базу не проходит и между устройствами не
синхронизируется. Регистрация не выдаёт сессию сразу: приходит 202 и требование
подтвердить почту, поэтому экран входа обязан уметь показать «письмо отправлено» и
предложить отправить его снова.

Google и Яндекс ведут в тот же аккаунт: при первом социальном входе Читавук создаёт
пользователя, при следующих находит или связывает существующего. Провайдер
открывается только в системном браузере. Итоговая сессия возвращается приложению
POST-запросом на случайный loopback-адрес `127.0.0.1`, поэтому токен не попадает ни в
адресную строку, ни в историю браузера.

Данные разделены: всё, что принадлежит Wolfy, лежит в схеме `wolfy` той же базы.
Библиотека сербских уроков и библиотека английских книг — разные вещи и пересекаться
не должны.

## 4. Как это работает: сценарии

### Открытие книги

1. Клиент отдаёт путь к файлу в ядро, получает метаданные и оглавление, затем
   запрашивает текущую главу. Следующая читается по требованию — открытие не зависит
   от объёма книги.
2. Читалка рисует главу газетным набором, ставит буквицу и помечает слова, уже
   лежащие в словаре книги.
3. У PDF одна физическая страница — одна единица навигации, и страницы без текста
   сохраняются тоже: иначе номера, оглавление и прогресс сдвинутся после иллюстраций.

### Тап по слову

1. Ядро локально отдаёт лемму, часть речи, разбор формы и частотность — карточка
   всплывает сразу, до всякой сети.
2. Одновременно ядро ищет русский эквивалент, английское толкование и МФА в офлайн-
   словаре. Его gzip-архив входит и в APK, и в Windows-установщик; после согласия
   пользователя файл ставится атомарно, без сети.
3. Параллельно уходит запрос за контекстным переводом предложения. Ответ доезжает в
   уже открытую карточку и кэшируется на обеих сторонах.
4. Произношение не уходит в сеть: Android использует `TextToSpeech`, Windows —
   системный `SpeechSynthesizer`.

**Порядок важен: карточка никогда не ждёт сеть, чтобы появиться.**

### Разбор фразы

Ядро отдаёт три независимых слоя, и клиент рисует их поверх одного текста:

- **находки** (`Finding`) — правило, формула, объяснение и диапазон слов;
- **роли** (`Role`) — подлежащее, сказуемое, дополнение, обстоятельство, связка;
   неоднозначная связь пропускается: неверный граф хуже неполного;
- **маркеры** (`MarkerKind`) — вспомогательный глагол, окончание, частица, предлог;
   именно они, а не «род», несут грамматику английского, и подсвечиваются отдельно.

Цвет назначается не правилу, а **семейству** правил (`Family`: время, залог,
наклонение, условие, сравнение, ссылка). Семейств шесть — столько цветов глаз ещё
различает; правил больше двадцати, и попытка дать каждому свой цвет превратила бы
страницу в шум.

### Отметки читателя

Выделение и решение разведены во времени: жест берёт кусок, панель рядом с
куском предлагает, что с ним сделать — разобрать, покрасить, записать заметку.
Ни один из вариантов не остаётся включённым после действия.

Так было не всегда: раньше над страницей висела полка «Чтение · Маркер ·
Заметка», и инструмент выбирали до жеста. Режим переживал действие, занимал
верх страницы постоянно и требовал выделять дважды — сперва узнать, что нужен
маркер, потом выделить снова. Панель действий (`ui/reader/AnnotateTools.kt`)
пришла на её место, а её положение считает `actionsPlace`: под последней
строкой выделения, а если внизу нет места — над первой.

Опору панель берёт у раскладки текста, а не у абзаца: абзац романа бывает выше
экрана, и панель под его нижней границей оказалась бы за краем страницы.
Границы строк выделения сообщает наверх сам `ReaderParagraph`.

### Слово уходит в колоду

Кнопка «в колоду» посылает `save_word` в сессию — слово ложится в локальную базу
немедленно, синхронизация отправит его при ближайшей возможности. Визуально слово
улетает по дуге в раздел карточек (`widgets/Flight.kt`), и на значке раздела
загорается отметка: действие обязано быть видимым, иначе читатель нажмёт второй раз.

### Тренировка

Очередь и статус колоды считает ядро (`srs/training.rs`), вид упражнения выбирает
`srs/drill.rs`: выбор из четырёх, сборка слова из букв, ввод по памяти, конструктор
фразы из блоков, заполнение пропуска. Ответ уходит командой `review`; планировщик
пересчитывает интервал, HP и время следующего показа с учётом интенсивности и
накопленной лёгкости. Напоминание считается там же и ставится системным
планировщиком платформы.

### Чтение с компаньоном

Профиль, внешность и режим чтения хранятся локально и синхронизируются как одна
версионируемая запись. В обычном чтении работает локальный движок событий и набор
из 100 реплик; сеть не вызывается. ИИ используется только по явному действию:
мнение о странице, вопрос по книге, пересказ или генерация набора реплик. Текст
книги передаётся как недоверенный фрагмент с лимитом, а ответ проходит серверную
проверку структуры и длины. Режим «Исследования» удалён и частью архитектуры не
является.

Дневной лимит Beta-обращений живёт единственным числом в `readingai.DailyLimit`;
текст сообщения о лимите собирается из него же. Интерфейс числа не повторяет: он
показывает остаток, который приходит с ответом сервера.

Локальная память компаньона хранит на устройстве проверенные ответы (кэш по
отпечатку входа, без текста книги), краткие пересказы глав и вопросы читателя.
В промпт следующего запроса уезжают только пересказы и вопросы: нажатие кнопки
вопросом не считается и памятью разговора не является.

Ключ кэша собирается из того, что читатель считает своим запросом. Мнение о
странице узнаётся по её тексту — там текст и есть вопрос. Вопрос о книге и
пересказ — по главе и месту в ней, огрублённому до двадцатой доли: прочитанное
прирастает каждой строкой, и в ключе оно означало бы, что один и тот же вопрос
за вечер задан дважды. На сервер прочитанное едет по-прежнему.

### Обновление

Проверка не зависит от аккаунта. Через четыре секунды после запуска клиент
запрашивает `/v1/update/latest`, затем повторяет раз в шесть часов. Сервер выбирает в
`WOLFY_RELEASES_PATH` пакет с наибольшей семантической версией и возвращает размер и
SHA-256. Клиент скачивает его в отдельный каталог, ограничивает объявленный размер,
проверяет хеш и атомарно сохраняет метаданные. Незавершённый или повреждённый файл не
может стать готовым обновлением.

До конца загрузки интерфейс не прерывает чтение. Затем сверху появляется кнопка
перезапуска. В Windows она копирует встроенный `wolfy-updater.exe` во временный
каталог, закрывает Wolfy, ставит MSI в пассивном режиме и открывает новую версию —
поэтому на машине пользователя не нужны ни Go, ни PowerShell, ни файлы из
репозитория. Сборка из Google Play использует Flexible In-App Update; прямая
debug-сборка скачивает APK, и системный установщик всё равно проверит подпись.

Linux проходит тот же путь до последнего шага: проверяет, качает, сверяет сумму —
и отдаёт готовый DEB системному установщику через `xdg-open`. Ставить пакет самим
нельзя (нужен root), но из «не ставим сами» не следует «не говорим»: раньше клиент
на Linux не проверял обновления вовсе и о новой версии молчал. DEB собирается в CI
и выкладывается рядом с MSI под именем `Wolfy-<версия>.deb` — по нему сервер и
узнаёт пакет платформы `linux`.

Отказ установки виден. Любая неудача — повреждённый пакет, ненайденный
`wolfy-updater.exe`, отсутствующее разрешение на установку — называет причину, и
кнопка остаётся на экране, предлагая проверить ещё раз. Молчащий отказ хуже
видимого: про видимый понятно, что делать дальше.

## 5. Кто чем владеет

| Данные | Владелец | Почему так |
|---|---|---|
| Библиотека, полки, прогресс, колоды | ядро (сессия) → файл на устройстве → сервер | Читать нужно офлайн; сервер только догоняет |
| Настройки | ядро (`settings`) | Один контракт для native и web; старые записи получают defaults |
| Серия дней и статистика тренировок | ядро (`practice`, CRDT) → сервер | Счётчики устройств сливаются, а не перетираются LWW |
| Файлы книг | устройство ↔ `bookfiles` на сервере | Байты крупные и живут отдельно от метаданных библиотеки |
| Профиль и реплики компаньона | клиент → sync → сервер | Реакции должны работать офлайн и одинаково на устройствах |
| Токен сессии | клиент, на устройстве | Пароль не проходит через базу Wolfy и не синхронизируется |
| Профиль рекомендаций | сервер | Должен быть одинаков в web и native-клиентах с первого запуска |
| Кэш переводов | обе стороны | Сервер экономит платные запросы, клиент — время |
| Офлайн-словарь | устройство | Условие чтения без сети |
| Пакеты обновлений | сервер (каталог на диске) | Выпуск — это копирование файла, без правки манифеста |

## 6. Оформление как часть архитектуры

Тема — не набор цветов, а объект: четыре темы (`Paper`, тёплая сепия, угольная,
OLED-чёрная), у каждой своя палитра грамматических семейств. Кегль и межстрочный
интервал настраиваются прямо над страницей чтения и записываются тем же объектом
настроек, который уже участвует в синхронизации, — иначе на втором устройстве книга
выглядит чужой.

Движение вынесено в `theme/Motion.kt` одним объектом длительностей и двух кривых:
`Paper` — для появления и переходов, `Toss` — для броска карточки в колоду. Настройка
«меньше движения» заменяет весь объект на `NoMotion`, и ни один экран об этом не
знает — анимации просто становятся нулевой длины. Это единственный способ не забыть
про доступность в двадцатом по счёту виджете.

Web повторяет то же правило через `motionFor` и CSS media query. Звуки компаньона
включаются отдельной настройкой: «меньше движения» не обязано делать приложение
беззвучным, а выключение звуков не меняет анимации, радио и произношение.

Буквица (`widgets/DropCap.kt`) считается по метрикам шрифтов, а не по подбору:
её высота — это две строки набора плюс высота прописной буквы, и кегль из этой
высоты выводится делением на долю прописной в шрифте буквицы. Доли лежат в
`theme/Typography.kt` рядом с объявлением семейств — из таблицы `OS/2` самих
файлов. Оттуда же следует выбор шрифта по букве: во Fraunces нет кириллицы, и
русскую главу открывает Playfair. Арифметику стережёт `DropCapMetricsTest`, в
вебе то же правило записано формулой в `calc()`.

Клавиатура и жесты — тоже контракт, а не украшение: `ui/nav/Shortcuts.kt` разделяет
перехват до потомков (читалка забирает пробел и стрелки у своего списка) и всплытие
после них (текстовые поля сохраняют цифры и Enter). `LocalKeyboard` говорит экранам,
показывать ли подсказки клавиш вообще.

## 7. Чего здесь осознанно нет

- **Своей регистрации и своего пароля.** Аккаунт один на два приложения.
- **Часов и генератора случайностей в ядре.** Всё приходит параметрами — иначе
  логику дат нельзя проверить тестом.
- **Кодогенерации DTO.** Пока их три ручных копии; долг записан выше.
- **Форматов кроме EPUB, TXT и PDF.** FB2, DOCX, MOBI и DJVU — в планах, а не в коде.
- **Догадок в грамматическом разборе.** Ложное срабатывание хуже пропуска: читатель,
  увидевший неверный разбор, перестаёт верить и верному.
