# Архитектура Wolfy

## Три слоя и почему их три

```
┌──────────────────────────────────────────────────────────┐
│           client/  Kotlin Compose Multiplatform          │
│                  Android · Windows                       │
└──────────┬───────────────────────────────────▲───────────┘
           │ HTTP + JSON                       │ FFI
┌──────────▼────────────────┐  ┌───────────────┴───────────┐
│       server/  Go         │  │      core/  Rust          │
│  общий с Читавуком вход   │  │  парсеры книг, токенизация│
│  синхронизация устройств  │  │  леммы, части речи,       │
│  прокси DeepL · словари   │  │  грамматические правила   │
│  OCR по фото страницы     │  │                           │
└───────────────────────────┘  └───────────────────────────┘
```

Разделение проходит по одной линии — нужна ли сеть.

Тап по слову обязан отвечать мгновенно, поэтому всё, что можно посчитать на устройстве,
считается в Rust: разбор формы, лемма, часть речи, частотность, грамматическая
конструкция предложения и поиск в скачанном словаре. Это работает в метро и
в самолёте.

Сеть нужна для контекстного перевода (DeepL знает предложение целиком
лучше любого локального словаря), синхронизации между устройствами и распознавания
страницы по фото. Их делает Go-сервер — заодно потому, что ключи провайдеров нельзя
класть в приложение, которое можно распаковать.

Ещё одна сетевая возможность — рекомендательная лента открытых изданий. Сервер читает
Atom-каталог Standard Ebooks, нормализует книги в общий тип `content`, ранжирует их по
локальным эмбеддингам интересов и проксирует загрузку EPUB. Тип контента задан явно,
поэтому тот же контракт можно расширить статьями и журналами без новой навигации и
без изменения профиля пользователя.

## Почему ядро на Rust, а не в Kotlin

Парсинг книги и токенизация — это единственное место, где приложение реально упирается
в процессор. Плюс один и тот же разбор нужен и на Android, и на Windows, и потенциально
серверу: один Rust-код вместо трёх реализаций, которые разойдутся через полгода.

## Общие аккаунты с Читавуком

Читавук выпускает непрозрачный сессионный токен. Wolfy хеширует его SHA-256 и
проверяет по общей таблице `sessions`, откуда получает `user_id`. Своей регистрации у
Wolfy нет — иначе появятся два пользователя с одной почтой.
Форма входа Wolfy передаёт почту, пароль и имя устройства в API Читавука. Wolfy
сохраняет только полученный сессионный токен на конкретном устройстве; пароль через свою базу не
проходит и между устройствами не синхронизируется.

Данные при этом разделены: всё, что принадлежит Wolfy, лежит в схеме `wolfy` той же
базы. Библиотека сербских уроков и библиотека английских книг — разные вещи и
пересекаться не должны.

## Что происходит при открытии книги

1. Клиент отдаёт файл в ядро, получает метаданные и оглавление, затем запрашивает
   текущую главу. Следующая глава читается по требованию, поэтому открытие книги не
   зависит от её полного объёма.
2. Читалка рисует главу газетным набором и помечает слова, уже сохранённые в словарь.
3. Тап по слову: ядро локально отдаёт лемму, часть речи, разбор формы и частотность —
   карточка всплывает сразу, до всякой сети.
4. Одновременно ядро ищет русский эквивалент, английское толкование и МФА в
   необязательном TSV-словаре. Его gzip-архив входит и в APK, и в Windows-установщик:
   после согласия пользователя файл ставится атомарно без сети. Публичные
   `/v1/define` и `/v1/dictionary` остаются резервом и путём будущего обновления.
5. Параллельно уходит запрос на сервер за контекстным переводом предложения. Ответ
   доезжает в уже открытую карточку и кэшируется на обеих сторонах.
6. Произношение не уходит в сеть: Android использует `TextToSpeech`, Windows —
   системный `SpeechSynthesizer`. МФА при этом берётся из того же словаря.
7. Кнопка «в колоду книги» кладёт слово в локальную базу; синхронизация отправит его
   на сервер при ближайшей возможности.

Порядок важен: карточка никогда не ждёт сеть, чтобы появиться.

У PDF одна физическая страница соответствует одной единице навигации. Ядро использует
постраничный API извлечения и сохраняет даже страницы без текста, чтобы номера,
оглавление и прогресс не сдвигались после иллюстраций.

## Рекомендательная лента

1. Раздел доступен только после входа общим аккаунтом Читавука.
2. При первом входе пользователь выбирает CEFR и жанры. Профиль хранится на сервере и
   поэтому одинаков на Windows и Android.
3. Сервер строит детерминированный локальный вектор по метаданным, описанию и жанрам.
   Профиль предпочтений складывается из выбранных жанров, отметок «нравится» и книг,
   добавленных в библиотеку. Интерфейс эмбеддингов отделён от источника каталога, так
   что модель можно заменить без изменения клиентского контракта.
4. Добавление сначала проверяет и загружает совместимый EPUB только с разрешённого
   HTTPS-хоста Standard Ebooks, затем автоматически записывает положительную реакцию.
5. Клиент сохраняет EPUB обычным путём библиотеки. После этого книга ничем не
   отличается от импортированной вручную и доступна офлайн.

## Карточка слова и фразы

Карточка имеет два режима. «Слово» показывает лемму, все найденные части речи,
конкретную словоформу, морфологические факты, CEFR, Zipf-частотность, длину и оценку
числа слогов. «Фраза» показывает точные диапазоны правил грамматического движка и
консервативные связи между исполнителем, действием, дополнением и определением.
Неоднозначная связь пропускается: неверный синтаксический граф хуже неполного.

Настройки темы, кегля и межстрочного интервала доступны прямо над страницей чтения.
Они записываются тем же объектом настроек, который уже участвует в синхронизации.

## Синхронизация

Last-write-wins по ревизии, которую присваивает сервер. Исключение — прогресс чтения:
там побеждает наибольшая позиция, иначе устройство, читавшее офлайн, откатит прогресс
второго. Подробности — в `rules/shared_protocol.md`.
