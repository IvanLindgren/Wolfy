2.1. Исправить cursor/snapshot race

Сейчас нельзя получать:

BooksSince(cursor)
CardsSince(cursor)
...
CurrentRev()

как несогласованные чтения.

Опасный сценарий:

A имеет cursor=10

A читает books -> увидел максимум 11

B записывает book с rev=12

A читает CurrentRev -> 12

A получает:
cursor=12
но book rev=12 отсутствует

После этого A запросит только:

rev > 12

и изменение 12 потеряно навсегда.

Требуемый инвариант

Если сервер возвращает:

cursor = N

то ответ должен включать все изменения

oldCursor < rev <= N

которые относятся к данному sync snapshot.

Изменение, созданное после snapshot N, обязано получить rev > N и приехать в следующий sync.

Требуемая реализация

Не использовать схему:

прочитал коллекции
...
потом отдельно узнал CurrentRev

Нужна одна согласованная транзакционная операция.

Допустимый вариант:

BEGIN

apply incoming mutations

snapshotRev = current user's sync revision

SELECT books
WHERE rev > oldCursor
  AND rev <= snapshotRev

SELECT cards
WHERE rev > oldCursor
  AND rev <= snapshotRev

прочитать остальные данные того же snapshot

COMMIT

return cursor = snapshotRev

Используй либо согласованный transaction snapshot, либо верхнюю границу rev <= snapshotRev во всех запросах.

Не возвращай CurrentRev, прочитанный после того, как набор данных уже сформирован.

Тест

Integration test с двумя PostgreSQL connections.

Нужно искусственно остановить sync A между чтениями, выполнить write B и продолжить A.

Проверить одно из двух корректных поведений:

A.cursor < B.rev

либо

A содержит B и A.cursor >= B.rev

Недопустимо:

A.cursor >= B.rev
&&
B отсутствует в A

Проверить и books, и cards.

3. P0 — Rust client merge не должен принимать ответы из прошлого

Даже после исправления сервера core должен быть defensive.

В apply_server старый HTTP response не должен откатывать уже более новое local clean state.

Сценарий:

request A
request B

response B -> cursor=20
response A -> cursor=19 приходит позже

После второго ответа запрещено:

cursor 20 -> 19
book.rev 20 -> 19
Требования

При применении server state:

state.cursor = max(state.cursor, incoming_cursor)

Для clean записи:

incoming.rev < local.rev

означает, что incoming надо игнорировать.

Dirty local mutation также нельзя перетирать старым response.

Существующая защита через Sent от изменения во время запроса должна сохраниться.

Добавить тесты:

новый response -> старый response

и

старый response -> новый response

Финальное состояние должно быть одинаково новым.

4. P0 — удалённые книги/карточки не должны воскресать от stale replica

Сейчас нельзя считать:

последний HTTP request = самая новая пользовательская воля.

Пример:

phone:
delete book X
sync

laptop:
старый offline snapshot
X ещё живая
меняет progress
sync позже

Старая копия не должна автоматически снять tombstone только потому, что HTTP пришёл позже.

Семантика

Удаление считается отдельным пользовательским mutation.

Stale update, основанный на версии до tombstone, не имеет права очищать deleted.

При этом пользователь должен иметь возможность сознательно добавить эту книгу снова.

Это два разных действия:

stale sync

и

explicit re-add/revive

Их нельзя различать по deleted=false.

Предпочтительный путь

Сделать explicit revive через Rust library operation.

Например:

planAdd(fingerprint)

для удалённой книги с тем же fingerprint может вернуть отдельный план:

revive / attachDeleted

После чего специальная команда Rust:

снимает tombstone;
сохраняет существующий ID;
привязывает файл;
делает запись dirty.

Обычный stale server/client record такую операцию изображать не должен.

Добавить тест:

delete rev=20
stale live rev=10
merge
=> deleted

И отдельный тест:

explicit re-add
=> книга снова живая
5. P1 — проблема одинакового source_key на двух устройствах

Не исправлять это удалением unique index.

Не исправлять это разрешением дубликатов.

Не исправлять это выбором первой найденной строки.

Сценарий:

phone offline:
id=A
source_key=HASH

desktop offline:
id=B
source_key=HASH

После sync должна существовать одна логическая книга, а все связанные:

cards;
progress;
annotations;
path-local state

должны продолжать ссылаться на неё правильно.

Перед реализацией сначала написать тест этого сценария.

Затем коротко зафиксировать выбранную canonical identity strategy.

Допустимы два серьёзных варианта:

Вариант A — deterministic canonical ID

Rust определяет ID книги из source_key.

Именно Rust, не Kotlin/TS.

Для существующих random IDs нужна migration:

old id -> canonical id

с перепривязкой cards и прочих связанных сущностей.

Вариант B — server alias/canonicalization

Сервер обнаруживает:

same source_key
different id

и выбирает canonical ID.

Но тогда sync protocol обязан явно сообщить:

oldId -> canonicalId

а Rust обязан атомарно переписать ссылки.

Если выберешь вариант B, учти не только cards, но и annotations.

Запрещено

Не делать:

DROP UNIQUE INDEX ...

и объявлять задачу решённой.

Не делать:

ON CONFLICT DO NOTHING

с потерей progress второго устройства.

Если корректное remapping требует слишком большого protocol migration — остановись после тестов/design note и сообщи об этом, а не делай половинчатый патч.

6. P0 — разделить preferences и тренировочное multi-device state

Сейчас настройки интерфейса и тренировочная статистика не должны жить как один LWW blob.

Эти поля имеют разную семантику.

Например:

theme             -> LWW допустим
fontScale         -> LWW допустим
reduceMotion      -> LWW допустим

onboardingSeen    -> OR

answers/right     -> grow-only counters
training days     -> set union
best streak       -> max/derived

Нельзя делать:

old laptop settings arrived last
=> answers 100 -> 80
=> today's training disappeared
Требуемая модель

Вынести practice state из обычных preferences.

Предлагаемая Rust структура:

PracticeState {
    days: BTreeSet<i64>,
    counters: BTreeMap<String, PracticeCounter>,
    best_floor: u32,
}

PracticeCounter {
    answers: u64,
    right: u64,
}

String key — persistent replica/device writer ID, который приходит извне.

Rust не генерирует его сам.

Training days

После ответа:

day = local_day(now_ms, offset_minutes)
days.insert(day)

Merge:

set union

Это:

commutative;
associative;
idempotent.
Current streak

Алгоритм:

today присутствует
    start=today
иначе yesterday присутствует
    start=yesterday
иначе
    0

Дальше идти назад, пока последовательные дни существуют.

Это сохраняет правило:

если занимался вчера, но ещё не сегодня, streak всё ещё жив.

Best streak

Результат:

max(
    best_floor,
    longest_consecutive_run(days)
)

best_floor нужен для migration старых состояний, потому что из старых полей невозможно восстановить всю историческую серию.

Counters

При локальном answer:

component = counters[deviceId]
component.answers += 1
if right:
    component.right += 1

Merge двух состояний:

для каждого device:
answers = max(left.answers, right.answers)
right   = max(left.right, right.right)

Итоговые totals:

sum всех component answers
sum всех component right

Проверить:

right <= answers
Важно

G-counter корректен только если один deviceId не имеет двух независимых writers.

Для web не разрешать двум вкладкам одновременно мутировать один и тот же persistent device component без координации.

Используй либо Web Locks/single-writer policy, либо явно докажи существующей архитектурой, что concurrent tabs не могут потерять increments.

Не добавляй этот caveat в Rust в виде платформенного хака.

Legacy migration

Старые:

trained_on
streak_days
best_streak
answers
right

нельзя просто выбросить.

При первой migration:

если:

trained_on = D
streak_days = N

восстановить минимально известный диапазон:

D-N+1 ... D

как training days.

Старый best_streak сохранить в best_floor.

Старые counters положить в специальный стабильный legacy component.

Migration должна быть idempotent.

Повторное открытие файла не должно второй раз добавлять answers.

7. Сервер не должен сам реализовывать PracticeState merge

Go не должен знать математику days/counters.

Лучше хранить practice blobs/components так, чтобы Rust мог получить несколько replicas и выполнить merge.

Например сервер может хранить per-device opaque state:

(user_id, device_id, practice_json)

и возвращать известные components клиенту.

Клиент передаёт их Rust core для merge.

Если выбирается другая транспортная схема — она всё равно не должна переносить CRDT business rules в Go.

Во время перехода поддержать старый sync payload, чтобы старое состояние не исчезло при обновлении.

8. P0 — annotations: сначала correctness, никакого умного GC
8.1. Полностью убрать unsafe tombstone GC из critical path

Текущая идея:

device seen_rev
MIN(seen_rev)

не доказывает, что устройство видело tombstone от другого writer.

Lamport 100 > 5 не означает:

replica с clock 100 обязательно видела operation clock 5 другого writer.

Поэтому в этом pass вообще не удаляй tombstones автоматически.

Не заменяй это:

delete after 30/90 days

Это хуже.

Оставить tombstones до отдельного протокола GC.

Добавить комментарий/TODO с чётким условием будущего GC:

tombstone можно удалить только после доказательства,
что каждая replica, способная прислать старое live состояние,
подтвердила snapshot, содержащий delete.

Если захочешь реализовать server generation + acknowledgements — это отдельный change с собственными protocol tests. Не тащи его «заодно».

Correctness сейчас важнее нескольких килобайт tombstones.

8.2. Исправить first-row race

Нельзя рассчитывать на:

SELECT ... FOR UPDATE

если row может ещё не существовать.

Перед lock:

INSERT INTO book_annotations (...)
VALUES (... пустой initial state ...)
ON CONFLICT DO NOTHING

После этого:

SELECT ...
FOR UPDATE

Теперь есть физическая row, которую конкурентная транзакция может заблокировать.

Test:

A first sync of same book
B first sync of same book
simultaneously

После обоих commit сервер обязан содержать union, а не A или B.

8.3. Merge должен иметь total ordering

Для одинакового ID winner обязан удовлетворять:

winner(a,b) == winner(b,a)

Основное сравнение:

Rev
Writer

При полном равенстве (Rev, Writer) записи в нормальном мире должны быть одинаковы.

Но повреждённый/старый клиент может прислать разные payload.

Поэтому нужен последний deterministic tie-break по всем значимым полям.

Не создавать key вида:

fmt.Sprintf("%s|%s|...", ...)

Разделитель может находиться внутри пользовательского текста.

Сравнивать поля типизированно в фиксированном порядке.

В tie-break включить всё, что может различаться:

Chapter
Start
End
Tone
Quote
Note
CreatedAt
UpdatedAt
Deleted
...

Если структура расширится — тест должен заставлять автора обновить comparator.

8.4. Normalize

Проверить и сохранить следующие правила:

duplicate IDs внутри одного snapshot -> ошибка;
ID после TrimSpace не может быть пустым;
ID длиннее лимита -> ошибка;
ID нельзя обрезать;
Quote/Note можно обрезать, если это продуктовая политика;
maxSpanTokens и maxQuoteRunes — разные constants;
Tone только валидный диапазон;
timestamps/revisions валидны;
End >= Start.

Если эти пункты уже исправлены — не переписывай код заново, только добавь/сохрани tests.

8.5. Limits должны быть round-trip safe

Сейчас нельзя допускать состояние, которое:

server может вернуть
но client не может отправить обратно

Развести понятия:

MaxActiveItems
MaxStoredItems
MaxSerializedBytes
MaxHTTPBodyBytes

Deleted tombstones не должны съедать business-limit активных заметок.

Но всё persisted state обязано иметь hard storage/byte limit.

Перед commit merged state:

посчитать active items;
проверить total stored;
сериализовать;
проверить serialized bytes.

HTTP body limit должен быть больше максимального допустимого serialized annotations payload с envelope overhead.

Никакого:

merged = merged[:limit]

При превышении — понятная ошибка, данные не менять.

9. Property tests для merge

Для annotations и остальных merge-функций обязательно проверить:

merge(a,a) == a                     idempotence

merge(a,b) == merge(b,a)            commutativity

merge(merge(a,b),c)
==
merge(a,merge(b,c))                  associativity

Можно не добавлять proptest, если это требует новую dependency.

Сгенерируй набор небольших состояний обычными nested loops/helper generators.

Особенно проверить:

equal Rev;
equal Writer;
delete vs live;
duplicate/corrupt payload;
differing positions;
Unicode Quote/Note;
empty states.
10. P0/P1 — resource limits сервера
Translate

Сейчас rate limit по количеству HTTP calls недостаточен, если внешний сервис тарифицируется по объёму текста.

Добавить hard limits до внешнего API.

Раздельные constants хотя бы для:

word/text
context

Не принимать десятки килобайт текста только потому, что весь JSON помещается в общий body limit.

До external request проверять длину в Unicode code points либо bytes согласно контракту провайдера.

Rate limiter должен учитывать не только request count, но и стоимость/размер хотя бы грубо.

Не ломать DB/cache hit: если перевод уже лежит в локальном cache, не обращаться повторно во внешний API.

OCR

Добавить:

per-user rate limit;
global concurrency limit;
hard encoded/decoded image size;
timeout;
проверку типа входа.

Не позволять одному authenticated account одновременно держать десятки дорогостоящих vision requests.

Semaphore не должен блокировать бесконечно — уважать request context cancellation.

Remote/discovery book downloads

remotebook уже имеет хорошую SSRF/resource защиту — не ослаблять её.

У discovery/download paths добавить аналогичный global concurrency bound, чтобы несколько одновременных 64 MiB books не занимали память процесса одновременно.

Лучше использовать общий downloader/gate, если это можно сделать маленьким изменением.

Не переписывать SSRF code ради унификации.

11. P0/P1 — Rust parser resource budgets

Любой файл книги считать недоверенным.

Ограничение compressed source size само по себе недостаточно.

Нужны центральные limits.

Не размазывать magic numbers по EPUB/TXT/PDF.

Например модуль:

parser/limits.rs

с понятными constants.

Не обязательно использовать именно эти значения без измерения, но должны существовать ограничения для:

max source bytes
max EPUB entries
max uncompressed EPUB entry
max total text produced from one chapter
max total extracted text
max TXT bytes
max PDF pages
max dictionary line bytes
max decoded image pixels/bytes where applicable
EPUB

Перед read_to_end/read_to_string проверить declared uncompressed size.

Но заголовку ZIP нельзя полностью доверять.

Поэтому само чтение тоже ограничить:

take(MAX + 1)

или эквивалентом.

Если реально прочитано > MAX — explicit error.

Не truncate.

Ограничить количество entries.

Не позволять zip bomb распаковать гигабайты из маленького EPUB.

TXT

Не делать бесконечный:

fs::read(path)

без предварительного metadata size check.

Для memory input тоже проверять bytes.len().

PDF

Ограничить:

source size;

Не менять архитектуру только потому, что другая кажется привычнее.

Не добавлять database только ради JSON state на сотни/тысячи записей.

Не переносить Rust rules в clients ради уменьшения FFI calls — наоборот, делать более крупные Rust queries.

Не писать полноценный dependency parser ради graph.

Не загружать весь EPUB в отдельную распакованную копию «для ускорения».

Не кешировать все chapters всех книг в RAM.

Не декодировать все изображения книги заранее.

Не удалять tombstones по времени.

Не чистить old devices автоматически без protocol, который заставляет вернувшееся retired device сначала получить полный authoritative snapshot.

Не делать random sleeps в concurrency tests.

Не выключать StrictMode React ради benchmark.

Не снимать lazyRouteComponent.

Не включать PDF.js в main bundle.

Не превращать content-visibility experiment в большой custom virtualization framework.

Не добавлять useMemo на каждую строку автоматически. Оптимизировать только hot paths.

Не делать «optimization», которая усложняет код, если profiler показывает <1ms и нет масштабирования по размеру данных.

37. Definition of Done

Работа считается завершённой только когда:

Correctness
sync cursor не перепрыгивает невидимые изменения

out-of-order response не откатывает state

stale replica не воскрешает tombstone

training с разных устройств не теряется

annotation merge commutative/associative/idempotent

concurrent first annotation sync не теряет одну сторону

corrupt state не превращается молча в пустой

unknown card review не считается тренировкой
Robustness
oversized/untrusted books получают controlled error

zip bomb не приводит к огромной allocation

paid APIs имеют per-request + concurrency limits

state write имеет recovery path
Performance
Kotlin не токенизирует каждый paragraph отдельным FFI call

word tap не вызывает десятки Rust crossings

web не сканирует весь token DOM для progress

web не извлекает все EPUB covers сразу

web не извлекает все chapter images сразу в scroll mode

web initial bundle остаётся в budget

disk/file work не тормозит UI thread
Compatibility
старые local JSON читаются

существующая библиотека сохраняется

paths остаются local

server не начинает получать файлы пользовательских книг

offline reading продолжает работать

web PWA продолжает работать

Android и Windows продолжают использовать тот же Rust source of truth
38. Финальный отчёт агента

В конце не писать просто:

Done, optimized sync.

Дать:

1. Какие bugs воспроизведены.
2. Корень каждого bug.
3. Какой invariant теперь выполняется.
4. Какие файлы изменены.
5. Какие migrations добавлены.
6. Какие старые persisted states проверены.
7. Какие concurrency tests добавлены.
8. Какие performance measurements были до/после.
9. Какие bundle sizes до/после.
10. Какие проблемы сознательно НЕ решались и почему.

Для performance писать числа только если они реально измерены.

Если изменение замедлило другой сценарий — это тоже указать.
